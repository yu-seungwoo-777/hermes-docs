## 2. 예상 프롬프트 (재구성)

릴스에서 "프롬프트만 입력하세요"라며 공유하는 문구는 영상에 전문이 나오지 않아,
데모 산출물 구조로부터 역설계한 **예상 버전**:

> **[2026-09-15 2차 갱신 — 승우님 제공 실측 단편 반영]**
> 영상 속 프롬프트의 일부가 실제로 확인됐다. 아래 2.1 참조.

### 2.1 실측된 프롬프트 단편 (승우님 제공)

```text
스킬이 영상 분석 결과를 낼 때는 항상 한국어로, 아래 형식을 따르게 SOUL.md 에 명시해줘.
- 후킹 멘트만 따로 강조해서 제일 위에
- 컷별 표: 타임스탬프 / 화면에 보이는 것 / 화면 텍스트 / 실제 대사
- "왜 이 구조가 먹히는지" 분석
- "내 콘텐츠에 적용할 점" 제안

추가로, 설치 끝나면 실제로 뭐가 깔렸는지 (yt-dlp, ffmpeg, 음성인식 도구 버전)
확인해서 결과 알려줘.
```

### 2.2 실측 단편이 말해주는 것 (설계 분석)

이 단편은 예상 버전보다 훨씬 정교한 설계 의도를 보여준다:

1. **출력 형식을 SOUL.md에 명시** — 스킬이 아니라 SOUL.md(페르소나/행동 규칙 레이어)에
   쓴다는 점이 핵심. 스킬은 "how to watch"(기술 절차), SOUL.md는 "how to report"
   (출력 계약)로 레이어를 나눠 관리한다. 이것은 Hermes의 SOUL/스킬 분리와 정확히 같은
   컨텍스트 엔지니어링 원칙이다.
2. **컷별 4칸 표 (타임스탬프/화면/화면텍스트/대사)** — 프레임(비전)과 자막(전사)을
   시간축으로 조인한 결과물 구조를 미리 강제한다. 이 표가 있으려면 파이프라인은
   프레임과 자막을 각각 따로가 아니라 정렬 가능한 형태로 남겨야 한다 — 출력 형식
   명시가 곧 데이터 스키마 명시다.
3. **후킹 멘트 강조** — 릴스 분석의 목적이 "이해"가 아니라 "재현"임을 드러낸다.
   도입부 0-10초를 특별 취급하는 것은 claude-watch의 "hook microscope"와 같은 발상.
4. **설치 검증 요구** — 스킬 생성이 끝나면 yt-dlp/ffmpeg/음성인식 도구의 실제 버전을
   확인해 보고하라는 지시. "에이전트가 산다고 믿지 말고 증명하라"는 검증 게이트.
   에이전틱 워크플로우에서 완료 보고의 신뢰성을 도구 버전 출력으로 담보하는 패턴이다.

### 2.3 예상 버전 (원본 — 역설계, 참고용)

```text
클로드, 네가 영상을 볼 수 있게 해주는 스킬을 만들어줘.

요구사항:
1. 스킬 이름은 claudewatch, .claude/skills/ 아래에 만들어줘.
2. 도구는 yt-dlp(다운로드) + ffmpeg(프레임 추출)을 사용하는 파이썬 스크립트로 만들어줘.
3. 유튜브/인스타/틱톡 링크 또는 로컬 영상 파일을 입력받아:
   - 장면 전환 기준으로 대표 프레임을 추출하고
   - 자막(음성)을 텍스트로 추출해서
   - 프레임 이미지 목록과 자막을 함께 정리한 index를 남겨줘.
4. 분석 요청을 받으면 프레임을 순서대로 직접 읽고(비전),
   화면 구성·텍스트·내용을 시간순으로 정리해 HTML 보고서로 만들어줘.
5. 60분 영상도 처리 가능하게 프레임 수 상한을 두고, 실패 시 재시도 로직을 넣어줘.

완성되면 이 릴스 링크로 시험해봐: <링크>
```

## 3. 설계 평가 (왜 이 구조가 맞는가)

### 핵심 통찰은 정확하다
- Claude의 네이티브 입력은 텍스트+이미지다. 영상 파일을 직접 받지 못하고,
  유튜브 링크를 주면 자막 트랙만 읽는다는 설명은 사실과 일치한다.
- "프레임을 추출해 이미지로 넘기면 모델이 본다" — 이것은 멀티모달 파이프라인의
  표준 패턴이고, 에이전틱하게는 "도구가 프레임을 만들고, 에이전트가 읽는다"의 역할 분담이다.

### 좋은 설계 포인트
- **스킬 = 절차지식, 도구 = 실행기** 분리: 프롬프트 한 줄로 Claude가 스스로 스킬을
  작성하게 하는 것은 에이전틱 코딩의 정석 (meta-skill: 스킬 만들기).
- 로컬 스크립트 실행이라 추론 비용 외 추가 과금이 없다는 것도 사실
  (단, "돈이 안 든다"는 프레임 수만큼 비전 토큰이 컨텍스트에 들어가는 비용은 존재).

### 한계 / 주의점 (릴스가 말하지 않는 부분)
- 프레임 수 상한 설계가 핵심: 60분 영상을 장면 전환 없이 1초당 1프레임으로 뽑으면
  3,600장 — 컨텍스트 한계 초과. 장면 전환 감지(scene detection) + 상한(24~32장) 조합이 필수.
- 자막 추출(whisper)은 로컬 CPU로는 60분 영상 처리에 수십 분 소요 가능 → "5분 만에"는
  GPU 또는 small 이하 모델 기준의 낙관적 수치로 추정.
- 인스타/틱톡은 로그인 벽이 있어 yt-dlp 실패가 잦음. 데모의 1분 릴스는 통과했겠지만
  실패율이 낮지 않아 재시도/대체 경로(fallback) 로직이 실무에서는 반드시 필요.

## 4. 구현 검증 (본 서버에서 실제 실행)

예상 프롬프트의 산출물을 그대로 구현해 검증했다.

- 스크립트: `scripts/analyze_video.py` (본 디렉토리)
- 파이프라인: yt-dlp → ffmpeg 장면전환 프레임 추출 → faster-whisper(small, ko) 자막
- 검증 소스: 릴스 원본 영상 28.5초 (페이스북 crawler 경로로 mp4 획득)
- 결과:
  - 프레임 7개 추출 (장면 전환 기준)
  - 자막 타임스탬프 정상 추출 (섹션 1의 전문과 일치)
  - index.json에 source/video/duration/frames/transcript 메타 정리 확인

에이전트가 이 index.json만 받으면 프레임을 비전으로 읽어 보고서를 쓰는 구조 —
릴스가 약속한 워크플로우와 동일하며, 실제 동작을 확인했다.

릴스의 `claudewatch`는 이 생태계의 바리에이션으로 판단됨. 데모 화면의 구조(장면전환 프레임+자막+HTML 리포트)는 claude-video/watch-video-skill 계열과 동일한 패턴.

### 설계 트렌드 시사점

1. **프레임 예산 자동화가 표준**: 고정 fps가 아니라 길이 기반 자동 스케일 + 하드캡(100장/2fps)이 업계 기본. 토큰 비용 폭발 방지가 1차 관심사.
2. **Whisper는 로컬→API 이동**: 로컬 whisper 설치 고통 때문에 Groq/OpenAI API(클라우드 전사)가 기본이 되고, 순수 stdlib HTTP로 SDK 의존 제거.
3. **트리거 가드**: 긴 영상의 우발적 토큰 소모를 막으려고 슬래시 명령 전용 트리거를 쓰는 패턴 등장 — "에이전트가 스스로 판단해 호출"의 부작용에 대한 반성형 설계.
4. **산출물의 영속화**: 채팅 답변이 아니라 구조화 노트/리포트 파일로 남기는 것이 차별점이 됨.
5. **검증 가능성**: watch-skill의 "증거+검증 계약"처럼 영상 분석을 관측가능성(observability)으로 승격하는 방향도 있음.

### 이 서버(Hermes)에 있는 유사 스킬

- `media/video-content-analysis` (agentarch 프로필): 페이스북/인스타 릴스 링크에서 og 메타→lookaside crawler mp4 추출→프레임+자막 절차 스킬. 이번 조사에서 실제로 사용·검증됨.
- `media/video-segment-capture` (content-creator 프로필), `media/youtube-content`, `media/songsee` 등이 media 카테고리에 존재.
- 차이: 위 스킬들은 "절차 지식"만 있고 프레임 추출 파이프라인 자체는 매번 조립. claude-video처럼 테스트된 실행기(scripts/)를 포함한 자기완결형으로 강화할 여지가 있음.
