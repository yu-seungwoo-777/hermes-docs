# "Hermes VPS 결과물을 Mac에서 확인하는 구조" 조사안 분석

- **날짜**: 2026-09-16
- **작성**: agentarch (에이전틱 코딩 설계 자문)
- **대상**: ChatGPT 등 외부 조사안 — "Hermes 작업 폴더 → 결과물 폴더 → 브라우저/파일앱에서 확인" 구조 제안
- **결론 요약**: **방향은 맞고, 출처도 대부분 실재·유효함.** 다만 인용의 근거 강도에 편차가 있고, 몇 가지 과장된/확인 불가한 서술이 있어 채택 시 보정이 필요함.

### 검증에서 추가로 확인된 사실 (조사안에 없는 것)

- Deliverable mode는 **kanban_complete(artifacts=[...])** 를 지원 — 칸반 워커가 완료 보고에 파일을 붙이면 게이트웨이가 구독 채팅에 첨부. 승우님의 오케스트레이션 체계와 직접 맞물리는 기능.
- `.py`, `.log` 등 소스 확장자는 **의도적으로 자동 첨부에서 제외** — 코드 결과물은 채팅 자동전달 대상이 아니라는 설계. 조사안의 "코드는 VS Code SSH" 역할 분담과 정확히 일치.
- hermes-workspace는 Tailscale/PWA 지원, auth 미들웨어·path-traversal 가드 내장 — 외부 노출(Cloudflare Tunnel) 시 보안 요소가 일부 마련돼 있음.
- 이슈 #531에 따르면 현재 메신저 업로드 파일은 `~/.hermes/document_cache/`에 24시간 TTL로 보관 — **업로드 원본의 영속 보관은 아직 구조적으로 해결 안 된 갭**.

## 2. 조사안의 구조 자체에 대한 평가

### 2.1 타당한 부분 (채택 권장)

1. **역할 분담 원칙** — "문서는 브라우저, 작업은 Hermes UI, 코드는 VS Code SSH, 대용량 영상은 파일 브라우저"는 도구의 강점에 맞는 올바른 분리입니다. 특히 deliverable-mode가 코드 파일 자동 첨부를 의도적으로 제외한다는 사실과 정확히 부합합니다.
2. **work/ vs outputs/ 분리 + README.md 규약** — 에이전트 산출물 관리의 핵심 원칙이 맞습니다. 에이전트는 "어디에 무엇을 남겼는지" 스스로 설명하지 않으면 재탐색 비용이 커지는데, README 규약이 이를 구조적으로 해결합니다. 구현 수단으로는 `AGENTS.md`(프로젝트 룰)에 규약을 적는 것이 정석입니다 — deliverable-mode 문서도 정확히 이 방식을 권장합니다.
3. **Cloudflare Tunnel + 도메인 노출** — 이미 보유한 인프라로 추가 비용 없이 시작하는 것은 합리적입니다.
4. **나중에 MinIO/R2로 outputs 분리 가능성** — 확장 경로로 타당합니다.

### 2.2 보정이 필요한 부분

1. **hermes-workspace는 커뮤니티(서드파티) 프로젝트** — 조사안이 마치 공식 UI인 것처럼 서술합니다. 공식 대안으로는:
   - `hermes dashboard`(공식 웹 관리 패널, 내장 TUI 챗) — 단 파일 브라우저 중심은 아님
   - `hermes desktop`(공식 네이티브 앱, Mac에서 실행) — 파일 미리보기 레일, 드래그앤드롭 지원. 원격 VPS 게이트웨이에 접속해 쓰는 구조가 공식 경로.
   - 채택 시: **공식 desktop 앱을 1순위, hermes-workspace는 파일 브라우저가 급할 때의 보조**로 두는 것이 안전합니다.
2. **"/outputs를 별도 웹 파일 브라우저로 노출"은 구체 수단이 비어 있음** — "files.example.com"이 무엇으로 구현되는지(예: filebrowser, SFTPGo, MinIO 콘솔, 혹은 hermes-workspace의 Files 페이지) 명시돼 있지 않습니다. 이것이 실제로는 가장 큰 구현 작업입니다.
3. **"Docker 환경에서 /output 공유 디렉터리" 주장의 출처 불명** — 인용 [1]은 deliverable-mode 문서인데 해당 내용이 문서에 없습니다. 별도 확인 불가(추정: Docker 설치 문서의 볼륨 마운트 안내를 섞어 인용한 것으로 보임).
4. **보안 논의 누락** — Cloudflare Tunnel로 파일 브라우저를 노출하면 인증 레이어(Cloudflare Access, 최소한 비밀번호)가 필수인데 조사안이 전혀 다루지 않습니다. PDF/영상이 아니라 **에이전트 작업 파일시스템 전체**가 노출될 수 있어 위험도가 높습니다.
5. **테이블의 ★ 평가는 근거 없는 주관치** — "Workspace ★5 / SCP ★2" 등은 검증 불가한 선호 서술. 참고용으로만.

## 3. 승우님 환경 기준 권장 설계

조사안을 수용하되, 다음과 같이 정정한 구성을 권합니다.

```
VPS
└── ~/workspace/
    ├── projects/ · research/ · drafts/     ← Hermes 작업 영역
    └── outputs/YYYY-MM-DD-<주제>/          ← 최종 산출물 (README.md 동봉 규약)

접근 경로 (우선순위 순)
1. Telegram 첨부          ← 산출물이 채팅으로 먼저 도착 (deliverable mode, 이미 사용 중)
2. Hermes Desktop (Mac)   ← 공식 앱, 원격 게이트웨이 접속, 미리보기 레일
3. 파일 브라우저 (웹)      ← 대용량 영상/대량 파일. Cloudflare Access 필수
4. VS Code Remote SSH     ← 코드/마크다운 편집
```

**핵심 수정사항 3가지:**

1. **1차 전달 경로는 이미 갖춰져 있음** — 승우님 체계는 Telegram 게이트웨이 + 칸반 `kanban_complete(artifacts=...)`를 이미 사용하므로, "Mac에서 확인"의 대부분은 조사안이 제안하는 웹 UI 구축 없이 해결됩니다. 웹 파일 브라우저는 **대용량/과거 파일 아카이브 열람**이라는 좁은 목적으로만 추가하는 것이 맞습니다.
2. **outputs 규약은 AGENTS.md에 명문화** — 조사안의 "규칙을 만들어둔다" 제안의 공식 구현 수단. 프로필별 SOUL.md가 아닌 워크스페이스 루트의 `AGENTS.md`에 두면 어떤 에이전트(Claude Code, Codex 포함)가 그 디렉터리에서 작업해도 동일 규약이 적용됩니다.
3. **웹 노출 시 보안 우선** — hermes-workspace든 filebrowser든 터널 뒤에 Cloudflare Access(또는 최소 basic auth)를 반드시 앞단에 두고, 노출 경로는 **outputs만** 마운트할 것(작업 영역 전체 노출 금지).

## 4. 요약 판정

|---|---|
| 제안 구조의 방향성 (역할 분리, outputs 규약) | ✅ 채택 권장 |
| 인용 [1] deliverable mode | ✅ 정확, 근거 충분 |
| 인용 [2] hermes-workspace | ⚠️ 실재하나 **서드파티** — 명시 필요 |

| 인용 [4] workspace/KB 이슈 | ✅ 실재하나 **P3 미채택 제안** — 로드맵 근거로 사용 금지 |
| 보안 논의 | ❌ 누락 — 채택 시 반드시 보강 |
| Docker /output 공유 주장 | ❌ 출처 불명 |

**총평**: 조사의 골격(폴더 규약 + 역할 분리 + 터널 노출)은 실전에서 통하는 설계이고 출처 조작은 없습니다. 그러나 (a) 서드파티 프로젝트를 공식처럼 서술, (b) 미채택 이슈를 기능처럼 서술, (c) 보안 공백 — 이 세 가지를 보정한 위 3장의 구성으로 실행하는 것을 권합니다.
