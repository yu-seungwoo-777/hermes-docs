# 범용 에이전트 스킬 표준안 (Universal Agent Skill Spec, v0.2)

- 일자: 2026-09-15 (v0.2 개정)
- 작성: agentarch (에이전틱 코딩 설계 자문)
- 목적: 승우님이 작성한 SKILL.md 스킬을 여러 코딩 에이전트(Claude Code, Codex CLI, OpenCode, Hermes)로 **재작성 없이 이식**하기 위한 표준안
- 범위 결정 (v0.2): **자작 스킬 이식 전용**. 서드파티 스킬 도입(남이 만든 스킬이 시키는 셸 명령을 내 에이전트가 실행하는 문제)은 본 표준안의 범위 밖이며, 필요 시 별도 "신뢰 경계" 문서로 분리한다.
- 개정 이력:
  - v0.1 (2026-09-15): 초안
  - v0.2 (2026-09-15): 승우님 리뷰 반영 — §4 자가설치 프로토콜 제거(부트스트랩 모순), 설치자 문서 분리, §5.1 실측 열 추가, §2.1 근거 표기 정정, §6 예시 상태 정정

## 0. 설계 목표와 배경

릴스(claudewatch) 사례와 외부 생태계 조사(bradautomates/claude-video 등)에서 확인된
문제: 같은 스킬이 하네스마다 경로·매니페스트·트리거 방식이 달라 재작성이 반복된다.

이 표준안의 목표는 재작성이 아니라 **이식**이다.

**사용 범위 결정**: 본 표준안은 승우님 자신이 만든 스킬의 이식만 다룬다. 따라서
설치는 "에이전트가 남의 문서를 읽고 판단하는" 문제가 아니라 정해진 절차의 실행이며,
표준안 본체에 설치자(installer) 문서 1개(§4)를 두는 것으로 충분하다. 스킬 본문에
설치 절차를 넣는 v0.1의 설계는 다음의 부트스트랩 모순으로 폐기했다:

> 모든 하네스에서 스킬 로딩 트리거는 description 매칭이고(§5.2), 인덱스에 오르려면
> 이미 파일시스템 복사가 끝나 있어야 한다. 즉 스킬 본문의 설치 절차를 에이전트가
> 읽을 수 있는 시점에는 설치가 이미 완료된 뒤다. 본문에 설치 절차를 두는 것은
> 닭과 달걀이다.

핵심 결정 (v0.2 기준 3가지):

1. **코어는 작게, 하네스 차이는 표와 설치자로** — 스킬 코어는 그 스킬만의 것
   (요구 도구, 검증 계약, 출력 계약)만 담고, 경로 지식은 가지지 않는다. 하네스별
   경로는 어댑터 표(§5)와 설치자 문서(§4)가 흡수한다. 하네스가 늘거나 경로가
   바뀌면 고칠 곳은 표와 설치자뿐, 배포된 스킬 전체가 아니다.
2. **설치는 스킬 밖의 설치자 문서가 담당** — 표준안 본체에 INSTALL 절차 1개.
   스킬마다 반복되지 않는다. (Hermes의 `hermes skills install`이 이미 "스킬 밖의
   설치자"라는 생태계 현실과도 일치.)
3. **기술 절차와 출력 계약의 분리(§3)** — "how to do"는 스킬 본문, "how to
   report"(언어·형식·강조)는 페르소나 레이어. 이 분리가 없으면 스킬마다 보고서
   형식이 흩어진다.

## 1. 용어

- **하네스(harness)**: 에이전트 실행기. Claude Code, Codex CLI, OpenCode, Hermes.
- **코어(core)**: 하네스 중립적인 SKILL.md 본문. 그 스킬만의 지식(절차·요구사항·
  검증 계약·출력 계약)을 담는다. 하네스별 경로·설치 지식은 담지 않는다.
- **설치자(installer)**: 표준안 본체에 하나만 존재하는 설치 절차 문서(§4). 하네스
  감지 → 경로 결정 → 복사 → 의존성 설치 → 검증을 수행한다. 스킬 밖에 둔다.
- **검증 계약(self-test contract)**: 스킬이 선언하는 "나를 어떻게 시험하고 성공을
  무엇으로 판정하는가". 설치자는 이 계약을 실행해 성패를 판정한다.

## 2. 코어 계약 (SKILL.md 최소 표준)

스킬 코어는 **그 스킬만의 것**을 담는다. 원칙: "스킬이 져야 할 책임은 자기 검증
계약이지, 남의 파일시스템 지식이 아니다."

### 2.1 프론트매터

```yaml
---
name: video-watch              # 소문자+하이픈, 1-64자, 디렉토리명과 일치
description: >                 # 1문장, 마침표 종결. 트리거 조건을 앞 57자 안에
  Analyze any video link or file into frames, transcript, and cut table.
license: MIT
compatibility: universal       # 이 표준안 준수 표시
metadata:
  spec: uass/0.2               # 표준안 버전
  output-contract: persona     # §3 출력 계약 사용 표시
  selftest: scripts/analyze_video.py --selftest   # §2.4 검증 계약 포인터
---
```

모든 하네스가 인정하는 공통 필수는 `name`, `description` 두 개뿐이다 (검증:

- Claude Code: name, description
- Codex CLI: name, description
- OpenCode: name, description (나머지 필드는 unknown 시 무시 — 공식 문서 확인)
- Hermes: name, description (validator는 version/author 등도 권장)

→ `name`/`description`만 필수로, 나머지는 선택. 미인식 필드는 하네스가 무시하므로
무해하다(OpenCode 공식 문서: "Unknown frontmatter fields are ignored").

**description 규칙**: 60자 내외 1문장, 마침표 종결, 마케팅 단어 금지.

**57자 근거의 정직한 표기 (v0.2 정정)**: "앞 57자" 규칙의 근거는 **Hermes의 실측
구현값**이다 — Hermes의 스킬 인덱스는 description을 57자+생략 부호로 절단한다
(시스템 프롬프트 구현 세부사항, 공식 문서 기재). 타 하네스(Claude/Codex/OpenCode)
의 인덱스 절단 길이는 미측정이다. 표준안은 이 값을 보수적 상한으로 채택하되,
v0.3 전에 타 하네스 절단 길이를 실측해 표를 갱신한다 (§7 후속 과제).
트리거 인터페이스가 description 하나뿐인 이상(§5.2) 이 제약은 표준안에서 가장
비싼 제약이므로, 근거 수준을 명확히 해두는 것이 중요하다.

### 2.2 본문 표준 섹션

```
# <스킬명> Skill
## When to Use        — 트리거 + 역트리거(Don't use for)
## Prerequisites      — 요구 도구·버전 (설치 방법이 아님. 설치는 §4 설치자가)
## How to Run         — 대표 호출 예
## Procedure          — 번호 단계, 각 단계에 검증 가능한 완료 기준
## Pitfalls           — 알려진 함정
## Verification       — 검증 계약: selftest 방법과 성공 판정 기준 선언
## Output Contract    — §3으로 위임했다면 그 취지 한 줄
```

규칙:
- 각 절차 단계는 **검증 가능한 완료 기준**으로 끝난다 ("요약하라" ✗, "수정된 파일
  전수 나열" ○).
- **설치 절차를 본문에 쓰지 않는다** (v0.2 핵심 변경). Prerequisites에는 "무엇이
  필요한가"(도구·버전)만 선언하고 "어디에 어떻게 깔리는가"는 설치자(§4) 소관이다.
  재설치 시나리오(허브 동기화, 기기 이전)를 위한 참고로 설치 힌트를 덧붙이는 것은
  허용하되, 의무 섹션이 아니라 부록 수준으로 강등한다.
- 하네스 고유 도구명을 코어에 직접 쓰지 않는다. 비전 읽기 같은 하네스 종속 단계는
  "영상 프레임을 네이티브 비전 도구로 읽는다"라고 기술하고, 구체 도구는 어댑터
  테이블(§5)이 매핑한다.
- 머신 로컬 절대경로 금지. repo-relative 또는 `~` 경로만.

### 2.3 폴더 구조 (자기완결 원칙)

```
<skill-name>/
├── SKILL.md            # 코어 (§2.2)
├── scripts/            # 실행기 + selftest (하네스 무관한 파이썬/셸)
├── references/         # 부가 문서 (SKILL.md 본문은 100-200줄 유지)
└── templates/          # 출력 템플릿 (예: 컷별 4칸 표)
```

**스크립트 동거 필수**: SKILL.md와 scripts/는 반드시 같은 폴더 단위로 복사 가능해야
한다. claude-video의 사후 분석 — scripts가 분리돼 배포되면 비-Claude 호스트에서
스킬이 dead on arrival이었다.

### 2.4 검증 계약 (self-test contract) — 스킬의 핵심 책임

스킬은 자신의 검증 방법을 **선언**한다. 실행은 설치자(§4)가 한다.

선언 요소 (SKILL.md `## Verification` + frontmatter `metadata.selftest`):

1. **selftest 명령**: 하네스/네트워크 없이 실행 가능해야 한다 (예: 합성 테스트
   파일 생성 → 파이프라인 실행 → 산출물 검증). 외부 네트워크가 필요한 selftest는
   그 사실을 명시하고 오프라인 폴백을 제공한다.
2. **성공 판정 기준**: 기계 판독 가능해야 한다 (exit code 0 + 산출물 존재 등).
   "대략 잘 되면" ✗.
3. **의존성 선언**: selftest가 요구하는 도구와 버전 (Prerequisites와 일치).

이 선언이 있으면 설치자는 스킬 내용을 이해할 필요 없이 계약만 실행해 성패를
판정한다 — 스킬과 설치자의 관심사 분리가 완성된다.

## 3. 출력 계약 레이어 (페르소나 분리)

기술 절차와 출력 규격은 다른 레이어에 둔다. 근거: claudewatch 릴스의 실측 프롬프트 —

> "스킬이 영상 분석 결과를 낼 때는 항상 한국어로, 아래 형식을 따르게 SOUL.md에
> 명시해줘. - 후킹 멘트만 따로 강조해서 제일 위에 - 컷별 표: 타임스탬프/화면에
> 보이는 것/화면 텍스트/실제 대사 - '왜 이 구조가 먹히는지' 분석 - '내 콘텐츠에
> 적용할 점' 제안"

이 지시의 요체는 스킬이 아니라 **페르소나 계층에 기록하는 출력 계약**이다.
스킬은 여러 개여도 보고서 형식은 일관된다.

하네스별 페르소나 레이어 매핑:

| 하네스 | 페르소나/행동 규칙 파일 |
|---|---|
| Claude Code | CLAUDE.md (전역: ~/.claude/CLAUDE.md) |
| Codex CLI | AGENTS.md (전역: ~/.codex/AGENTS.md) |
| OpenCode | AGENTS.md / opencode.json rules |
| Hermes | SOUL.md (프로필별) |

규칙:
- 출력 계약이 스킬 고유하면 스킬 본문 `## Output Contract`에 둔다.
- 여러 스킬이 공유하는 프로젝트 공통 형식(언어, 표 양식, 강조 규칙)이면 페르소나
  레이어에 두고, 스킬 본문에서 "보고서 형식은 페르소나 계약을 따른다"고 참조만 한다.
- 컷별 4칸 표(타임스탬프/화면/화면텍스트/대사)처럼 데이터 스키마를 강제하는 형식은
  templates/에 파일으로 동봉하고 본문에서 참조한다 — 형식 명시가 곧 데이터 스키마
  명시다 (프레임+자막을 시간축 조인 가능하게 유지하라는 요구사항으로 번역됨).

## 4. 설치자 (Installer) — 표준안 본체에 1개

v0.1의 "스킬 본문 내 자가설치 섹션"은 부트스트랩 모순(§0 참조)으로 폐기하고,
설치 절차를 **스킬 밖의 단일 문서**로 분리한다. 이 절차는 모든 자작 스킬에 공통
적용되며, 스킬마다 반복되지 않는다.

### 4.1 설치 절차 (하네스 불문 공통)

1. **하네스 감지**: 대상 하네스를 확인한다.
   - `~/.hermes/` 존재 → Hermes
   - `~/.claude/` 존재 → Claude Code
   - `~/.codex/` 존재 → Codex CLI
   - `~/.config/opencode/` 존재 → OpenCode
   - 복수 감지 시: 설치 대상을 사용자에게 묻는다.
2. **경로 결정**: 어댑터 표(§5.1)에서 설치 경로를 조회한다.
   - 단, 실측 열이 "미실측"인 경로는 복사 전 실제 디렉토리를 먼저 확인한다.
3. **복사**: 스킬 폴더 전체(SKILL.md + scripts/ + references/ + templates/)를
   복사한다. 폴더명 = frontmatter `name`. (Hermes는 카테고리 하위로,
   `hermes skills install <path-or-url>` 사용 가능 — 보안 스캔 경유.)
4. **의존성 설치 + 버전 보고**: Prerequisites에 선언된 도구를 설치하고, **실제
   버전 출력을 그대로 보고한다** (`yt-dlp --version` 등 — "설치했다"가 아닌
   출력 증명).
5. **검증 게이트**: 스킬의 검증 계약(§2.4)을 실행한다. `metadata.selftest` 명령을
   돌려 성공 판정 기준과 대조한다.
6. **완료 보고**: 설치 경로 + 도구 버전 출력 + selftest 결과 3종 세트.
7. **실패 시**: 1회 재시도 → 재실패 시 사용자에게 블록 보고. 무리한 우회 금지.

### 4.2 근거: 완료 주장의 산출물 담보

릴스 실측 프롬프트의 "설치 끝나면 실제로 뭐가 깔렸는지 (yt-dlp, ffmpeg, 음성인식
도구 버전) 확인해서 결과 알려줘"는 신뢰 모델이다: 에이전트의 완료 주장을 산출물
(도구 버전 출력, selftest exit code)로 담보한다. v0.2에서 이 규칙의 소재를
스킬에서 설치자로 옮겼다 — 책임 소재가 명확해졌을 뿐, 규칙 자체는 그대로 살아
있다.

### 4.3 자작 스킬이므로 생략되는 것

서드파티 스킬 도입 시 필수인 신뢰 검증(스킬이 시키는 셸 명령의 안전성 검토,
출처 확인, 샌드박스 실행)은 자작 스킬에는 불필요하다 — 작성자가 본인이기 때문.
이것이 본 표준안을 자작 전용으로 한정한 이유다. 훗날 서드파티 도입이 필요해지면
§4.1의 1~3단계 사이에 "신뢰 경계 검토" 단계를 신설한 별도 문서를 만든다.

## 5. 하네스 어댑터 테이블

### 5.1 스킬 탐색 경로 (v0.2: 실측/출처 열 추가)

| 하네스 | 전역 | 프로젝트 | 출처 신뢰도 |
|---|---|---|---|
| Claude Code | `~/.claude/skills/<name>/` | `.claude/skills/<name>/` | 공식 문서 (미실측 — v0.3 전 실측 예정) |
| Codex CLI | `~/.codex/skills/<name>/` | `.codex/skills/<name>/` | **서드파티 가이드 (미실측)** — v0.3 전 실측 필수 |
| OpenCode | `~/.config/opencode/skills/<name>/` | `.opencode/skills/<name>/` | **공식 문서 (2026-09 확인)** |
| OpenCode (호환) | `~/.claude/skills/`, `~/.agents/skills/` 도 읽음 | `.claude/skills/`, `.agents/skills/` | 공식 문서 확인 |
| Hermes | `~/.hermes/skills/<category>/<name>/` | `<project>/.hermes/skills/`, `.agents/skills/` | 공식 문서 + **본 서버 실측** |

**v0.2 정정**: v0.1은 OpenCode(공식)와 Codex(서드파티)를 동일한 신뢰도로 나열했다.
경로가 틀리면 그 한 칸만 깨지는 게 아니라 설치 루프 전체가 깨지므로(§4.1 2단계),
각 칸의 출처 신뢰도를 명시하고 미실측 칸은 §4.1 2단계의 "복사 전 실측" 규칙으로
방어한다. Codex 칸이 가장 위험하다 — 서드파티 가이드 단일 출처이기 때문.

**공용 디렉토리 발견**: `.agents/skills/`는 OpenCode와 Hermes가 모두 읽는 크로스툴
경로다(양쪽 공식 문서 확인). 최대 호환성을 원하면 **`~/.agents/skills/<name>/`
단일 복사로 OpenCode+Hermes 동시 커버**가 가능하다. Claude Code와 Codex는 각자
경로가 필요하다.

### 5.2 트리거 방식

| 하네스 | 스킬 로딩 방식 | 트리거 |
|---|---|---|
| Claude Code | 스킬 인덱스 시스템 프롬프트 노출 → 모델 판단 로드 | description 매칭 (자율) 또는 /스킬명 |
| Codex CLI | skills 디렉토리 스캔 | description 매칭 (자율) |
| OpenCode | `skill` 도구로 on-demand 로드, available_skills 목록 제공 | description 매칭 + permission 설정 가능 |
| Hermes | skills_list/skill_view 도구 | description 매칭 (자율) |

공통 함의: **description이 사실상 유일한 트리거 인터페이스**다. 그래서 §2.1의
57자 규칙(근거: Hermes 실측, 타 하네스 미측정)이 중요하다. 우발적 토큰 소모가
우려되는 무거운 스킬은 OpenCode의 permission `ask`, 또는 본문에 "슬래시 명령으로만
호출" 가드를 권장한다 (watch-video-skill의 선례).

### 5.3 도구 능력 매핑 (비전 읽기 등)

| 능력 | Claude Code | Codex CLI | OpenCode | Hermes |
|---|---|---|---|---|
| 이미지 읽기 | Read (멀티모달) | 확인 필요 | 모델 의존 | vision_analyze (네이티브) |
| 셸 실행 | Bash 도구 | 셸 네이티브 | 셸 | terminal |
| 웹 추출 | WebFetch 등 | 네이티브 | 네이티브 | web_extract |

스킬 작성자는 능력 차이가 있는 단계(예: 프레임 읽기)에 분기를 둔다:
"네이티브 비전 도구가 있으면 그것으로, 없으면 프레임을 모델 컨텍스트에 직접
첨부 가능한 경로로 전달" 식으로.

## 6. 준수 예시: video-watch 스킬 (v0.2 상태 정정)

v0.1은 이 스킬을 "첫 준수 사례"라 썼으나 selftest가 미구현 상태였으므로 정확히는
**미준수 예시**였다 (지적 반영). 현재 상태와 준수 경로를 명시한다.

**현재 갖춘 것 (검증 완료)**:
- 파이프라인: yt-dlp(2026.08.19 실측) → ffmpeg 장면전환 프레임 → faster-whisper
  자막 → index.json (타임스탬프 자막 포함)
- 실데이터 검증: 페이스북 릴스 원본 28.5초에서 프레임 7장 + 자막 추출 성공
- scripts/ 동거 (§2.3 충족)

**미충족 (표준안 대비)**:
- selftest 미구현 → §2.4 검증 계약 위반. **스펙(§4.1 5단계)이 과한지 구현이 덜
  된 건지의 답: 구현이 덜 된 것이다** — selftest는 스킬의 핵심 책임(§2.4)이므로
  스펙을 낮추는 것이 아니라 구현을 보강한다.
- templates/ (컷별 4칸 표) 미동봉 — §3의 "형식=스키마 명세" 원칙상 동봉이 정답.
  "권장"이 아니라 준수 조건으로 정정한다.

**v0.2 준수 만들기 작업 (후속)**:
1. `analyze_video.py --selftest` 추가: ffmpeg로 합성 3초 클립 생성 → 파이프라인
   실행 → 프레임 1장 이상 + transcript 파일 존재 + exit 0 판정 (오프라인, 네트워크 불요)
2. `templates/cut-table.md` 동봉 (컷별 4칸 표 스키마)
3. frontmatter에 `metadata.selftest` 포인터 추가

완료 시 이 스킬은 명실상부한 첫 준수 사례가 되고, 본 표준안의 실행 가능성 증명이
된다.

## 7. 트레이드오프와 미해결 과제

1. **Codex 칸이 최대 리스크** (v0.2 신설): 유일한 서드파티 출처 칸. §5.1의 방어
   규칙(복사 전 실측)으로 완화하지만, v0.3 전에 `~/.codex/skills/` 직접 실측으로
   해소하는 것이 정답.

   (frontmatter + 필수 섹션 + selftest 존재 체크 linter)는 별도 과제.

   실행하는 신뢰 경계 문제는 본 표준안 범위 밖(§0, §4.3). 필요 시 별도 문서.
