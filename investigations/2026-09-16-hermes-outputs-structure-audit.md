## 2. 실측 결과 상세

### 2.1 outputs 구조: 미구현
- `/root/workspace`, `/root/outputs`, `/root/.hermes/workspace` 모두 없음.
- agentarch 프로필의 `/root/.hermes/profiles/agentarch/workspace/`는 **빈 디렉터리**.
- 즉, 앞선 보고서들의 핵심 권장사항(원본 저장소 + AGENTS.md 규약)이 실행된 적이 없음.

### 2.2 `/root` 직하위에 흩어진 산출물 (무규약)
| 파일/폴더 | 내용 추정 | 생성 |
|---|---|---|
| `kid_drawing.png`, `adult_20.png`, `adult_20_photo.png` | 이미지 생성 산출물 | 8/31 |
| `video-watch.zip` | 스킬 패키징 부산물 | 9/15 |
| `protest-page/` | HTML 프로젝트 (index/handoff/PROJECT.md) | 9/12 |
| `mailto-test/` | HTML 테스트 + .git | 9/12 |
| `docs/` | 문서 2개 (8/22) | 8/22 |
| `outbox/` | 인증서 1개 | 8/22 |
| `Sync/` | **빈 폴더** | 8/20 |

이 파일들은 어느 채널 첨부로도 전달된 이력을 보장할 수 없고, "어떤 태스크의 결과물인지" 폴더 구조로 추적되지 않는다.

### 2.3 `/root/reports` (hermes-docs): 규약은 우수, 운영이 규약 미준수
README 규약 자체는 우수(커밋 컨벤션·BOM·불변 원칙 명문화). 그러나 실측:

1. **미커밋 88건** — `daily/` 86건(8/31부터 전부) + 기타 2건이 전혀 커밋되지 않음. 마지막 커밋은 오늘(agentarch 조사 보고서 4건)이지만, **일일 보고 체계는 8/31 이후 단 한 번도 커밋·푸시되지 않음** → GitHub에서 daily 열람 불가 상태. 각 프로필이 "자기 보고서는 자기가 커밋" 규약을 지키지 못하고 있음.
2. **`state-db-repair/`에 229MB 이물질** — DB 덤프·복구 백업(repaired-dryrun.db, dump.sql 등 34개 파일)이 문서 저장소 작업 트리에 존재. `.git`이 65MB로 커져 있어 일부 대용량 파일이 히스토리에 섞인 정황. **문서 저장소의 목적과 불일치.**
3. **`designs/`, `incidents/` 빈 폴더** — 만들어졌으나 한 번도 사용되지 않음. 설계 문서가 별도 경로로 흘러가고 있다는 신호.

### 2.4 칸반 워크스페이스: 정상
- `/root/.hermes/kanban/workspaces/`에 12개 t_* 워크스페이스(총 224KB), attachments 3파일 — 용량·개수 모두 건강. 태스크 격리 구조는 잘 작동 중.

## 3. 권장 조치 (우선순위 순)

### 즉시 (데이터 손실 위험 해소)
1. **daily 86건 커밋·푸시** — 각 프로필(또는 오케스트레이터가 일괄)이 자기 파일을 커밋. 현재 상태로는 서버 디스크 장애 시 2주 치 일일 보고 소실.
2. **`state-db-repair/`를 문서 저장소에서 이동** — `/root/attic/state-db-repair/` 등 비(非)git 경로로. 이미 히스토리에 들어간 대용량 blob이 있다면 별도 정리 검토(rewrite는 리스크가 크니 우선 이동만).

### 단기 (이번 논의의 실행)
3. **`/root/workspace/` 생성 + AGENTS.md 규약 작성**
   ```
   /root/workspace/
   ├── AGENTS.md          ← outputs 규약 (YYYY-MM-DD-<주제>/ + README.md 동봉)
   ├── outputs/
   ├── work/
   └── archive/
   ```
   - 위치 근거: 모든 프로필이 접근 가능한 공용 경로. 프로필별 `~/.hermes/...`가 아닌 이유 = 산출물은 프로필이 아니라 "태스크"의 소속이기 때문.
4. **`/root` 직하위 흩어진 산출물 소속 이동** — protest-page, mailto-test, docs, outbox → `/root/workspace/archive/` 또는 프로젝트별 outputs로. 이미지 3개·zip은 판단 후 archive.

### 중기 (운영 안착)
5. **비어있는 designs/ 활용 또는 제거** — 설계 산출물이 실제로 여기 안 오고 있다면 폴더 목적을 재정의하거나 삭제해 혼란 제거.
6. **cron output의 local 전송 경로 점검** — `cron/output/`이 비어 있어 "local 저장"을 쓰는 작업이 있는지 확인 필요 (현재는 무해).

## 4. 채널 첨부와의 연결 (앞선 논의 수렴)

이번 실측이 앞선 4건의 보고서 결론을 확정한다:
- **원본 단일 저장소(outputs)가 실제로 없었으므로**, "채널 첨부 = 유일한 사본" 상태였던 파일들이 존재했을 가능성이 높다. deliverable mode는 참조 경로의 파일을 업로드할 뿐 원본을 보장하지 않는다 — outputs 구축의 실효 근거.
- Syncthing Stage 3도 **outputs가 존재해야** 성립. 구조가 먼저다.

## 5. 본 보고서의 한계

- 이미지 3개·zip 등은 파일명으로 내용을 추정한 것이고, 어떤 태스크에서 생성됐는지는 세션 기록까지 뒤어야 확정 불가.
- daily 미커밋의 원인(각 프로필 미실행 vs 오케스트레이터 지시 누락)은 이 세션에서 단정하지 않음 — 오케스트레이터(default) 확인 필요.
- 조치 1·2번(타 프로필 파일 커밋, 디렉터리 이동)은 agentarch의 안전 규칙상 직접 수행하지 않았음 — 오케스트레이터 지시 또는 승우님 승인 후 실행 권장.
